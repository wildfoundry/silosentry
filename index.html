SiloSentry

This site exists to answer one question: what is Dataplicity? SiloSentry is the made-up grain-bin IoT company we use so the answer isn’t abstract — you can see the same remote-ops loop a real OEM would live in.

Start with the idea See the loop

What Dataplicity is

Remote access and ops for Linux devices — after they leave the factory.

Not a grain-data SaaS. Not a VPN product you babysit. Dataplicity is the control plane between your team and boxes in the field: they call out over ordinary internet, show up in your account, and stay reachable for UI, shell, alerts, and fleet work — without opening inbound ports.

Without it

Every site is a snowflake: VPN configs, port forwards that die on LTE, “can you reboot it for us?”, truck rolls for a stuck service, no shared picture of what the fleet looks like this week.

With Dataplicity

Install an agent once. The device appears. Open its local web UI in the browser. Drop to a terminal when it’s wedged. See who’s quiet. Run the same fix across many. Keep doing that for years.

SiloSentry’s product is temperature and moisture in grain bins. Dataplicity is how their support team keeps those Linux gateways operable after the install crew leaves the elevator.

The core loop

Four moves. Everything else is scale.

If you only remember this, you understand Dataplicity. Pulse and fleet jobs are how a company like SiloSentry runs that loop across dozens of sites — they aren’t the starting definition.

  1. Ship with an install A one-liner at first boot. Outbound TLS only — works behind farm routers and LTE.
  2. It shows up The gateway lands in the org, tagged by site and SKU. Support can find it without asking for an IP.
  3. Reach it Wormhole opens the device’s local admin over HTTPS. Terminal is break-glass when a process is stuck.
  4. Know when it’s quiet Alerts and an ops overview tell you something needs a human before harvest calls pile up.

Step 2 — it shows up

This is the fleet you support

Not a metaphor. In Dataplicity, SiloSentry’s gateways are rows you can search: Probe GWs in bins, Site Gateways at the truck dump. Same list whether the co-op is in Grand Forks or Amarillo.

Look for: device names, classes, the org name SILOSENTRY in the sidebar.

Step 3 — reach it

Open a shell without a truck

When a service wedges, SiloSentry doesn’t wait for someone on site with a keyboard. The terminal is in the browser, next to the same device record — even if the box is currently offline, the path is obvious for when it comes back.

Look for: the selected gateway, Terminal in the middle, Pingüino for safe command help.

Step 4 — know when it’s quiet

Morning starts with attention, not archaeology

Dataplicity isn’t only “SSH in the cloud.” Ops needs a front door: what’s alarming, what’s offline, what still needs triage. That’s how SiloSentry decides whether today is a single tower or a whole region.

Look for: Needs ack / Alarms / the “fleet is offline” tip — the scan before deep work.

At company scale

Once the loop is clear, SiloSentry has to run it across a fleet.

This is the part that used to feel like a screenshot tour. Read it as “what Dataplicity becomes when you ship hardware for years” — not as the definition itself.

Progression — Device Class Pulse

Online isn’t the same as “still normal”

A gateway can be online and still wrong: probe-daemon gone, disk climbing. Pulse learns what Probe GW usually looks like, then shows who left that normal over time. That’s Dataplicity helping ops understand fleet change, not just presence.

Look for: “1 devices are drifting”, the spike on the drift chart, process / disk signals.

Action — fleet jobs

One guarded command, many devices

When harvest is close, SiloSentry doesn’t paste the same systemctl is-active into twenty-nine chats. A fleet job runs it across the set with history — Dataplicity as the place work happens, not just where you look.

Look for: running vs completed jobs, progress counts, the readiness command itself.

Proof — job detail

Which boxes succeeded matters

“We ran a fix” isn’t enough when a co-op is loading trucks. Per-device results close the loop: who returned active, who failed, who still needs break-glass.

Put together

One ops day, in Dataplicity terms.

If someone asks “so what do you actually do in it?”, this is the answer.

Morning

Scan attention → open the class

Operations overview first. Then Pulse on Probe GW: coverage is fine, one tower drifted. That’s the Dataplicity presence + progression story in ten minutes.

Midday

Run a fleet job

Restart the drifted service, or sweep readiness before harvest. Watch per-device results. This is Dataplicity as the action plane.

Afternoon

Break-glass on the leftover

Whatever the job didn’t clear gets Wormhole or terminal on that one record. Alerts keep whatever is still offline from disappearing into Slack noise.

Takeaway

Dataplicity is the remote-ops spine. SiloSentry is just the setting.

Swap grain bins for chargers, cameras, or cold-chain nodes — the loop stays: install outbound → show up → reach → know → act at scale.

Reach Linux devices after they ship — then run the fleet that grows around them.
