SiloSentry

You’re looking inside a working IoT company that ships Linux gateways into grain elevators — and runs them afterward on Dataplicity. The useful part isn’t the SKU list. It’s how the fleet progresses: what “normal” looks like for a class, when a device drifts, and how ops acts.

Inside the company

Their product is bin telemetry. Their support plane is Dataplicity.

Co-ops buy gateways and a cloud app for temperature and moisture. SiloSentry’s ops team lives in Dataplicity: which elevator, which SKU, who’s online, what’s drifted, what ran last week.

The working org

Twenty-nine gateways across Plains elevators

Probe GWs hang in bins. Site Gateways sit at the truck dump and scale house. Device classes stand in for SKUs; Networks stand in for co-ops. When support picks up the phone, they open this list — not a VPN spreadsheet.

Device Class Pulse

Watch the class learn “normal” — then see who leaves it.

Online/offline tells you a box is quiet. Pulse tells you a quiet box still looks like its peers — or that Tower 2 stopped running probe-daemon three days ago while coverage stayed full.

On the Probe GW class

One device drifting from normal

Fingerprints land on a cadence: OS, process set, disk, agent version. The class overview surfaces the story ops cares about — what’s different, how many devices, and when the drift started climbing on the chart.

  • Process set — probe-daemon missing vs peers
  • Root disk — fill above the class normal
  • Coverage — 24 of 24 still reporting, so this isn’t “lost”

Open the Pulse tab

Progression over time, not a single alert

Drift stays flat for weeks, then steps up when Tower 2 changes. Signal groups (storage, processes, agent) keep the finding explainable — so the next action isn’t “SSH everything,” it’s “fix that tower.”

Fleet jobs

When Pulse (or harvest) says “act,” run one command across the set.

SiloSentry doesn’t paste the same shell one-liner into twenty-nine tickets. A fleet job carries a guarded command to selected devices with retries and a history ops can reopen later.

Before harvest

Readiness, log vacuums, remediations

The jobs list is the company’s muscle memory: confirm probe-daemon on critical bins, vacuum journals after disk pressure, restart the tower Pulse already flagged. Running and completed sit in one place.

Open a job

Per-device success, not a vague “done”

A readiness sweep isn’t finished when the dialog closes. Ops wants which gateway returned active, which failed, and who still needs a human. That’s the same record they’ll cite when a co-op asks what ran before harvest.

When one box won’t cooperate

Fleet tools handle the many. Break-glass finishes the one.

If the job fails on Tower 2, SiloSentry still opens that gateway’s record — Wormhole into the local UI, or a browser terminal — without a truck roll or a public IP.

The leftover device

SS-GF-01 · Silo A — Hard Red Spring

One record holds agent version, class, organisation, and the path into Wormhole or Terminal. This is where the progression story ends for a single box: Pulse said it drifted, the job didn’t clear it, a human finishes it here.

Wormhole & terminal

Local UI over HTTPS. Shell when the process is wedged.

Edge gateways usually host a small admin page on localhost — Wormhole publishes that. When journals and service restarts are the only path left, the browser terminal is still in the same SiloSentry org, next to Pingüino for safe command suggestions.

In practice

What that progression looks like on one ops day.

Same tools, in order — attention → class drift → act across many → finish the leftover.

Morning

What needs you right now

Operations overview is the morning scan: alerts waiting, detections, whether the fleet offline spike is maintenance or a real outage. Then ops opens Probe GW Pulse — coverage full, one device drifting.

Mid-morning

Act with a fleet job

Restart probe-daemon on the drifted tower, or run the harvest readiness sweep if the co-op is loading trucks tomorrow. Watch per-device results before anyone drives out.

Afternoon

Break-glass on whatever’s left

If a job fails, open that device. Wormhole or terminal. Alerts stay in the inbox for anything still offline after the remediations — so the day doesn’t end as a pile of unread Slack pings.

Later

Ship more hardware

New Probe GWs join the class. Pulse folds them into “normal.” The progression story continues — class → drift → jobs → break-glass — without reinventing support.

Takeaway

Inside the company, Dataplicity is the ops spine.

Class = SKU. Network = site. Pulse = how the fleet changed. Fleet jobs = how you act on many. Wormhole and terminal = how you finish the one that won’t cooperate.

Ship → learn class normal → watch drift over time → run jobs → break-glass on the leftover.
