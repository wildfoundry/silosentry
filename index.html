Show me the devices Show me company ops

In one line: Dataplicity is the post-ship device ops platform; SiloSentry is a fake OEM we use to show what that looks like in practice — not a product you can buy, and not a replacement for “random tools” bolted together.

Why this isn’t tool salad

Not “PagerDuty + Geckoboard + a VPN spreadsheet.”

Those products each do a job. An IoT OEM needs those jobs attached to the same device records — from install through monitoring, paging, fixes, warranty, and RMA.

Scattered tools

A wallboard here, an on-call pager there, remote shells somewhere else, RMA in another system. Every incident starts with “which box was that?”

One spine (Dataplicity)

The device is the unit of work. Dashboards, incidents, terminals, and fleet jobs all point at the same fleet — including commercial lifecycle (licences, warranty, RMA).

1 · After devices ship

SiloSentry’s gateways land in Dataplicity — and stay reachable.

This is the foundation. Everything else (dashboards, pages, jobs) hangs off these records.

  1. Install outbound A first-boot command. Outbound only — works on LTE and farm routers.
  2. It shows up The gateway appears in the SiloSentry org, tagged by site and hardware type.
  3. Reach it Open the device’s local web UI, or a browser terminal, without a truck roll.
  4. Act on many Alerts, drift detection, and fleet commands — still keyed to those devices.

What you’d see

The supported fleet

Gateways named for bins and sites. Classes for SKUs (Probe GW, Site Gateway). This list is what SiloSentry’s support team opens when a co-op calls.

When one box needs a human

Terminal on that same record

You’re not jumping to a separate VPN tool. The shell is on the device page — next to the same identity dashboards and incidents will refer to.

2 · Running the company

Ops wall, incidents, progression, remediations — same account.

This is the “what would my company look like?” part: not a feature dump, the shapes SiloSentry would actually use day to day.

Ops center

A monitoring wall fed by your devices

Not a generic KPI collage. SiloSentry’s “Plains elevators” display is built from their Dataplicity fleet and monitors — check-ins, map, on-call strip.

Incidents

Page people about things that already exist here

A tower’s probe service down. Customer-cloud latency. Ack, own, escalate, publish — with the device or endpoint named on the incident.

On-call

Who gets woken

Escalation paths and mobile alerts live beside those incidents — not a separate vendor login your team forgets the password to.

Fleet progression

Online isn’t always “healthy”

Device Class Pulse watches whether gateways still look like their peers over time — e.g. a missing service or climbing disk — so ops sees change, not just up/down.

Fixes at scale

Run a command across many gateways

Harvest readiness checks, restarts, cleanups — as fleet jobs with per-device results. The same place that paged you also runs the remediation.

3 · A day in the seat

If you were SiloSentry ops on Dataplicity.

Morning

See what needs you

Operations overview, the ops wall, Pulse on the Probe GW class.

Midday

Page → fix

Acknowledge the Tower 2 incident. Run a fleet job. Check per-device results.

Afternoon

Finish the leftover

Terminal or Wormhole on the one box that didn’t clear. Alerts for anything still quiet.

Ongoing

Lifecycle stays attached

Customers, licences, warranty, RMA — still in the same product. Hardware support didn’t end at install day.
